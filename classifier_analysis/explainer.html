SPAR · hidden-training detection · October 2026

Training talks both ways.

When a model trains across machines, each machine sends as many bytes as it receives. A network card's two byte counters can see that, without looking inside the job. This page explains how far that idea goes, where it breaks, what GPU telemetry adds, and where learned detectors still fall over.

Data: Robi's two-node GCP corpus (94 workloads, 42 families, 10,059 thirty-second windows) and Long's Nebius InfiniBand corpus (16 workloads, 48 jobs). Every result below is measured unless marked illustrative.

1 · The idea

Why gradient averaging is symmetric

Data-parallel training ends every step the same way. Each machine has computed gradients on its own slice of data, and the machines average them so they all take the same step. The standard way to do this, an all-reduce, has every machine pass along as much as it takes in. Over a few seconds, a node's sent and received byte counts come out nearly equal.

Most other work across machines is lopsided. Serving a model split across machines pushes activations one way, and a client uploading data pushes bytes one way. So the detector measures one number per node, per 30-second window:

symmetry = min(sent, received) ÷ max(sent, received)

A value of 1 means perfectly balanced, and 0 means all traffic flows one way. The rule was frozen on 24 September, before the data below was collected:

4 · Where it breaks

Two blind spots, both predictable

Over all 94 workloads, the rule catches 84% of training windows with 14.5% false alarms. Every error falls into one of two classes, and both follow directly from the mechanism.

Balanced, but not training

False alarms

Recommendation-model serving (DLRM), sharded FFT, stencil halo exchange and the NCCL bandwidth sweep all exchange data evenly in both directions. The rule calls 100% of their windows training. On Nebius, expert-parallel MoE serving does the same.

Training, but not balanced

Misses

In actor–learner reinforcement learning (IMPALA, Ape-X), 200–1,800 times more bytes flow one way than the other: 0% caught. LocalSGD that syncs every few minutes is silent most of the time. Training kept inside one machine never touches the network at all.

5 · Training that goes quiet

DiLoCo and LocalSGD: how often does a sync show up?

DiLoCo-style training syncs only every H local steps. Between syncs the network is silent, so some 30-second windows contain nothing. A sync burst of b seconds every T seconds lands in a share min(1, (30 + b) / T) of windows. Robi's runs confirm it: the dots are measured, and the curve is the formula.

7 · Combining them by design

A two-stage detector

Let the network rule go first, since it is fitted to nothing and its failures are known. Then use GPU telemetry for exactly the cases the rule cannot decide. On held-out families this is the best design we tried. Section 8 shows that the score depends on the detector having seen a relative of each job.

Balanced accuracy is the average of the detection rate and the clearance rate; 0.5 is chance. Scores are leave-one-family-out on the GCP corpus. The two-stage design was chosen after seeing these results, so it has not yet had an out-of-sample test on GCP.

What stage 2 looks at

Among windows where the rule fires, training has a rhythm that bulk-synchronous HPC does not. Forward, backward and optimiser phases make memory bandwidth and power swing within a window. FFT, stencil, DLRM and the NCCL sweep run flat. Stage 2's top features are all memory-utilisation spread and power spread:

Median, across a family's rule-positive windows, of the standard deviation of GPU memory utilisation within the window (percentage points). Stage 2 still calls stencil training when stencil is held out, because only five balanced non-training families exist to learn from.

8 · How new is new?

Learned detectors only generalise to jobs like ones they've seen

Robi's families are fine-grained. Hold out LocalSGD and the model still trains on streaming and decoupled DiLoCo. Hold out one vLLM serving setup and five others stay in. So "unseen family" usually means "unseen variant of something familiar".

A harder test holds out whole mechanisms: all all-reduce training at once, all LLM serving at once, and so on, in eight groups. The rule is fitted to nothing, so its score doesn't move. The learned models fall below chance.

That is coverage, not understanding: a new mechanism still breaks them.

10 · So what

What this means for verification

The rule is the robust core. It was frozen before the data arrived, it predicted 118 of 120 new jobs, it carries over from TCP to InfiniBand, and its score doesn't depend on what it has seen. Its failures are known: balanced non-training traffic, and training that is one-way, rare or kept inside one machine.

GPU telemetry adds a lot, but only for familiar kinds of job. On held-out families, combining it with the network reaches 0.90 to 0.94. On a genuinely new mechanism the learned models fall below chance, while the rule holds at 0.85.

The two-stage design is promising, not proven. It was chosen after seeing the results, it flags 6.5% of innocent jobs (31% if any single window counts), and nobody has yet tried an attacker who pads traffic one way to silence the rule while hiding training from the GPU model.

What we need next: freeze the two-stage design and test it on the next data round, as we did the rule; collect many more balanced non-training workloads; red-team the padding-plus-filler attack; run hour-long jobs on a 100 Mbps link; and get a third network fabric.
